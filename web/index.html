Research, not a claim

What R1 tests

Can a simple hash-based, authenticated construction be a useful baseline for further work? R1 separates its stream and authentication keys with HKDF-SHA-256, generates counter blocks with HMAC-SHA-256, and authenticates before releasing plaintext.

The first result is negative: more overhead and lower throughput. That stays in the record.

What a proof would need

Precise privacy and integrity games, explicit primitive assumptions, quantitative bounds, composition analysis and independent scrutiny. We have proof obligations, not a finished proof.

Known ways it fails

Reuse a key and nonce and the stream repeats. The attack bench demonstrates plaintext recovery from that mistake. Raw APIs cannot enforce fresh nonces. The browser generates a new nonce per encryption.

It does not hide length, prevent replay, establish keys, sign messages, or protect a compromised browser. Memory erasure is not guaranteed.

Not the same job

AES encrypts data. RSA supplies public-key operations. ML-KEM establishes shared keys, while ML-DSA and SLH-DSA sign. A symmetric envelope cannot replace all of them or win a meaningful single leaderboard.

Mathematically uncrackable?

Perfect secrecy is possible under strict one-time-pad assumptions: a uniformly random, independently shared key as long as the message, never reused. It doesn't provide authentication or solve key delivery. A short reusable key cannot offer perfect secrecy for arbitrary longer messages. R1 makes no unconditional, quantum-proof, or best-on-earth claim.
